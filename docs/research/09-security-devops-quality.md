# Security Engineering, CI/CD, and GitHub Automation for Lumen

> Researched: 2026-10-05 · Scope: threat modeling, filesystem-attack defenses for a cleanup tool, IPC security, static analysis/supply chain, GitHub Actions hardening, repo governance, release automation, hooks, and CI code signing.

## Summary

- **The core safety risk is path confusion, not malware.** CVE-2022-21658 (Rust `remove_dir_all` TOCTOU) and gh CLI v2.102.0's Sept 2026 symlink-write fix show that "check path, then act on path" is unfixable; Lumen must act only through directory handles/fds with identity re-verification (dev+inode / volume+FileId).
- **Defensive primitives exist on every desktop OS**: `openat/unlinkat/renameat` + `O_NOFOLLOW`/`AT_SYMLINK_NOFOLLOW`; macOS `O_NOFOLLOW_ANY` (11+) and `renameatx_np(RENAME_EXCL|RENAME_SWAP)`; Linux `openat2(RESOLVE_BENEATH)`, `renameat2(RENAME_NOREPLACE)`; Windows `FILE_FLAG_OPEN_REPARSE_POINT` + `SetFileInformationByHandle(FileDispositionInfoEx POSIX_SEMANTICS / FileRenameInfoEx with RootDirectory)`.
- **APFS is normalization-insensitive but stores names unnormalized; macOS default is case-insensitive, iOS case-sensitive.** Never use string equality for policy decisions; compare identities; escape bidi/control characters everywhere names are displayed or sent to Jev.
- **cap-std 4.0.3** gives directory-capability containment (good for scanners) but does not address hard-link races or identity checks; a dedicated `rustix`-based executor crate is still needed.
- **IPC**: XPC with `setCodeSigningRequirement` (quote the Team ID); Windows named pipes need an explicit DACL (default grants Everyone read) plus `first_pipe_instance`; UDS with `SO_PEERCRED`/`getpeereid`; Tauri capabilities deny-by-default with no generic fs plugin. Privileged side accepts plan IDs, not paths.
- **CodeQL Rust is GA** (2.23.3, Oct 2025) in default and advanced setup, plus an `actions` language for workflows. Semgrep CE Rust is single-function only and registry rules are license-restricted; Opengrep is the LGPL fork. Use Semgrep/Opengrep for custom "ban raw fs deletes" rules.
- **Supply chain incidents in 2026 are concrete**: the Trivy/TeamPCP attack (Mar 2026) started with `pull_request_target` and spread via force-pushed action tags. Pin every action by full SHA, enforce via org policy, and run zizmor + actionlint.
- **GitHub defaults moved fast**: `pull_request_target` runs from the default branch (Dec 2025); checkout v7 blocks pwn-request patterns (Jul 2026); workflow execution protections GA (Sept 17 2026) with `pull_request_target` disabled by default on public repos from **Nov 2 2026**; Dependabot default 3-day cooldown (Jul 2026).
- **Dependency updates**: prefer Renovate (pnpm v12, digest pinning, `minimumReleaseAge`) because Dependabot docs still list pnpm only to v10; use pnpm's own `minimumReleaseAge` (1 day default since v11), `trustPolicy: no-downgrade`, `blockExoticSubdeps`.
- **Provenance**: `actions/attest@v4` (supersedes attest-build-provenance) needs `id-token`, `attestations`, `artifact-metadata: write`; private repos require Enterprise Cloud; SLSA Build L3 needs a reusable build workflow. Turn on immutable releases.
- **Runners (Oct 2026)**: `macos-latest` = macOS 26 arm64, `windows-latest` = 2025 with VS 2026, `ubuntu-latest` = 24.04; pin explicit labels.
- **Governance**: rulesets + merge queue (checks must run on `merge_group`) + CODEOWNERS on safety/executor/IPC/workflow paths; release-please v4 manifest mode for the polyglot monorepo; `gh pr merge --auto --squash --delete-branch --match-head-commit`; lefthook for hooks.
- **Signing**: notarytool with App Store Connect API key + stapler; Windows via Azure Artifact Signing (~$9.99/mo; individuals USA/Canada only; no instant SmartScreen trust, EV no longer helps).
- **Do not open archives**; scan huge trees iteratively with bounded resources, failing closed to REVIEW.

## Findings

### 1. Threat modeling methodology
- STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege) applied per element/data flow of a DFD remains the default; the [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) frames it as four questions (what are we building, what can go wrong, what are we going to do about it, did we do a good job). OWASP Threat Dragon and Microsoft Threat Modeling Tool both support STRIDE.
- LINDDUN (KU Leuven) covers privacy: Linking, Identifying, Non-repudiation, Detecting, Data disclosure, Unawareness, Non-compliance; it is referenced by ISO/IEC 27550. LINDDUN GO is a card-based lightweight variant ([LINDDUN GO categories](https://linddun.org/linddun-go-categories/)). "Detecting" matters for Lumen: the mere existence of an artifact (e.g., a cache for a dating app, a VPN, a medical app) disclosed via telemetry/evidence export is a privacy leak even without file contents.
- Attack trees are the right tool for the single most important abuse case: "Lumen deletes or exfiltrates data the user did not intend". Root goal decomposed into: (a) path confusion (symlink/junction/TOCTOU/normalization), (b) policy bypass (Jev output treated as decision, rule mis-evaluation), (c) IPC spoofing (unprivileged process drives privileged helper), (d) supply chain (malicious crate/npm/action), (e) update channel compromise.
- OWASP [Desktop App Security Top 10](https://owasp.org/projects/desktop-app-security-top-10) (DA1 Injections ... DA10 Insufficient Logging & Monitoring) is a usable checklist for the Tauri/desktop shell; DA5 Improper Authorization and DA9 Known-vulnerable components map directly onto IPC and supply chain controls.

### Threat model sketch for Lumen (STRIDE x key assets)
| Element | S | T | R | I | D | E |

### 2. Filesystem attack classes and defensive APIs

**The canonical lesson: CVE-2022-21658.** Rust's `std::fs::remove_dir_all` (Rust 1.0.0-1.58.0) checked "is this a symlink?" and then recursed, a TOCTOU race that let an attacker swap a directory for a symlink and trick a privileged program into deleting arbitrary trees. The fix (Rust 1.58.1) uses `openat()` with `O_NOFOLLOW` plus `unlinkat()` on Unix and handle-based native APIs on Windows; the advisory explicitly states "preemptive permission checks cannot mitigate this, they face identical race conditions" ([GHSA-r9cc-f5pr-p3j2](https://github.com/rust-lang/rust/security/advisories/GHSA-r9cc-f5pr-p3j2)). As recently as gh CLI v2.102.0 (2026-09-30) GitHub fixed `gh release download`/`gh run download` writing "remote content to an unintended local file when the destination contained symbolic links" ([cli/cli releases](https://github.com/cli/cli/releases/latest)): this bug class keeps recurring in mature tools.

**Attack classes relevant to a cleanup tool**
- *Symlinks / junctions / mount points*: a user-writable cache dir replaced by a link to `~/Documents` or `C:\Windows`. On Windows, junctions and directory symlinks are both reparse points; `CreateFileW` follows them unless `FILE_FLAG_OPEN_REPARSE_POINT` is passed. Mount points (bind mounts, APFS firmlinks, Windows volume mount points) let a traversal silently cross devices: compare `st_dev` (Unix) / volume serial + file ID (Windows) to the scan root and refuse to cross.
- *TOCTOU in delete/move*: any "stat path, decide, then act on path string" sequence is racy. Decide on an **open handle/fd** and act relative to that handle (`unlinkat(dirfd, name, ...)`, `renameat(srcdirfd, name, dstdirfd, name)`), and re-verify identity (dev+ino / FileId) right before acting.
- *Path traversal*: names containing `..`, absolute components, or (Windows) alternate data streams `file:stream`, device names (`CON`, `NUL`, `COM1`), trailing dots/spaces, `\\?\` and `\\.\` prefixes, 8.3 short names (`PROGRA~1`). Never build a destination path by concatenating untrusted names; resolve beneath a directory handle.
- *Unicode normalization (APFS)*: APFS stores names as UTF-8 **without normalizing**; since macOS 10.13/iOS 11 both variants are normalization-insensitive via hashing ("normalization variants of a filename cannot be created in the same directory, and ... a filename can be found with any of its normalization variants"); case-insensitive is the macOS default, iOS is case-sensitive; directory hard links are not supported on APFS ([Apple APFS FAQ](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)). Consequence: Lumen must never use string equality on paths for policy matching (allow/deny lists, "already quarantined" checks). Compare by file identity, or canonicalize both sides (NFD + case fold per volume capability) and only for display/rule matching, never for the act itself. Linux ext4 is byte-exact (except casefold dirs); NTFS is case-insensitive by default but per-directory case sensitivity exists.
- *Case-insensitivity*: `Cache` vs `cache` rules; a rule protecting `~/Library/Mobile Documents` must match regardless of case on case-insensitive volumes.
- *Hard links*: deleting one link of a multiply linked file does not free space and may remove a name the user depends on. Report `st_nlink > 1` as REVIEW, and do not count it toward reclaimable bytes. APFS clones also share blocks: reclaimable bytes are not `st_size`. cap-std explicitly notes hard-link races are not addressed by its design ([cap-std README](https://github.com/bytecodealliance/cap-std)).
- *Malicious filenames*: newlines, control characters, ANSI escapes, U+202E RIGHT-TO-LEFT OVERRIDE (e.g. `invoice\u202Efdp.exe`), zero-width joiners, homoglyphs, invalid UTF-8 (Unix) / unpaired surrogates (Windows). Risks: log injection, UI spoofing of what will be deleted, prompt injection into Jev, CSV/JSON export injection. Store paths as raw bytes (`OsString`/`Vec<u8>` / WTF-16), render with an escaping display function that makes control/bidi characters visible.

**Defensive APIs (Unix / macOS)**
- `openat(dirfd, name, O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC)`, `fstatat(..., AT_SYMLINK_NOFOLLOW)`, `unlinkat(dirfd, name, 0 | AT_REMOVEDIR)`, `renameat(...)`.
- macOS 11+: `O_NOFOLLOW_ANY` makes `open` fail with `ELOOP` if **any** component is a symlink, not just the last ([Malwarebytes on macOS 11](https://www.malwarebytes.com/blog/mac/2021/08/macos-11s-hidden-security-improvements); cap-std tracks adopting it in [issue #179](https://github.com/bytecodealliance/cap-std/issues/179)). Go's `os.Root` discusses the same flag ([golang/go#73079](https://github.com/golang/go/issues/73079)).
- macOS `renameatx_np(fromfd, from, tofd, to, flags)` with `RENAME_EXCL` (fail with `EEXIST` if destination exists, the analogue of Linux `RENAME_NOREPLACE`) and `RENAME_SWAP` (atomic exchange); newer SDKs also define `RENAME_NOFOLLOW_ANY` (unverified: confirm in the installed SDK's `<stdio.h>` before relying on it). Linux: `renameat2(..., RENAME_NOREPLACE | RENAME_EXCHANGE)`, `openat2(..., RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV)` (Linux 5.6+).
- Rust: `rustix::fs::{openat, statat, unlinkat, renameat, renameat_with}` with `OFlags::NOFOLLOW`, `AtFlags::SYMLINK_NOFOLLOW`, `RenameFlags::NOREPLACE` give safe, typed wrappers (rustix version unverified; pin via Cargo.lock).

**Defensive APIs (Windows)**
- Open with `CreateFileW(..., FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS)`, inspect `FILE_ATTRIBUTE_REPARSE_POINT` and the reparse tag via `GetFileInformationByHandleEx(FileAttributeTagInfo)`, refuse to descend into reparse points, and keep the handle open.
- Delete by handle: `SetFileInformationByHandle(h, FileDispositionInfoEx, ...)` with `FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS` (name disappears when the handle closes even if others have it open) and optionally `IGNORE_READONLY_ATTRIBUTE` ([FILE_DISPOSITION_INFORMATION_EX](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex)). `STATUS_CANNOT_DELETE` means read-only or mapped view.
- Move by handle: `SetFileInformationByHandle(h, FileRenameInfoEx, FILE_RENAME_INFO{Flags, RootDirectory, FileName})`; `RootDirectory` lets the target be resolved relative to a directory handle **only when `FileName` is relative**; an absolute `FileName` silently ignores `RootDirectory`, so the executor must assert the target name is a single leaf component (no `\`, `/`, `:`, drive prefix). With `FileRenameInfo`, `ReplaceIfExists = FALSE` errors on an existing target; with `FileRenameInfoEx` the same no-replace behaviour is obtained by not setting `FILE_RENAME_FLAG_REPLACE_IF_EXISTS` ([FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info)). `FileRenameInfoEx`/`FileDispositionInfoEx` are Windows 10-era classes and POSIX semantics are not honoured by every filesystem (FAT/exFAT, some SMB servers return `ERROR_INVALID_PARAMETER`/`ERROR_NOT_SUPPORTED`); Rust std's post-CVE `remove_dir_all` falls back to classic `FileDispositionInfo` in that case, and Lumen's executor needs the same explicit fallback path (and must treat the fallback as "delete pending until last handle closes"). Use NT path prefix `\\?\` for long paths.
- Identity: `GetFileInformationByHandleEx(FileIdInfo)` gives volume serial + 128-bit FileId for re-verification.

**cap-std (Bytecode Alliance)**: `cap_std::fs::Dir` is a capability: all paths are relative to the `Dir`; `..`, absolute paths, and symlinks that would escape return `PermissionDenied`. Linux 5.6+ uses `openat2(RESOLVE_BENEATH)`, FreeBSD 13 `O_RESOLVE_BENEATH`, elsewhere component-by-component resolution. Current version 4.0.3 ([docs.rs](https://docs.rs/cap-std/latest/cap_std/)). Related: `cap-fs-ext` (extra metadata/`FollowSymlinks` options), `cap-tempfile`. Caveats: not a sandbox against unsafe code; hard-link races not addressed; Windows supported but semantics differ.


### 3. IPC security
**macOS XPC.** Use `xpc_connection_set_peer_code_signing_requirement` (macOS 12+) on the listener/connection, or `NSXPCConnection.setCodeSigningRequirement(_:)` (macOS 13+) ([Apple docs](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:))). Apple DTS: the check is a real cryptographic code-signing validation; do **not** roll your own with `SecCodeCheckValidity` on a PID (TOCTOU / PID reuse). Recommended requirement: `anchor apple generic and certificate leaf[subject.OU] = "TEAMID"` optionally `and identifier "com.lumen.app"` ([forum 773573](https://developer.apple.com/forums/thread/773573)). Always quote the Team ID: a Team ID that starts with a digit unquoted causes a requirement syntax error and SIGABRT ([forum 801478](https://developer.apple.com/forums/thread/801478)); validate strings with `csreq -r req.txt -t`. A privileged helper should be installed via `SMAppService` (see platform research docs) and expose a minimal, typed command set (e.g., `quarantine(plan_id)` taking a server-side plan, not raw paths).

**Windows named pipes.** Default pipe DACL grants full control to LocalSystem, Administrators, creator owner and **read to Everyone and Anonymous** ([Named Pipe Security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)), so always pass an explicit security descriptor (SDDL granting the interactive user's SID or logon SID; MS recommends the logon SID to block other sessions). Use individual rights instead of `FILE_GENERIC_WRITE` because `FILE_APPEND_DATA` == `FILE_CREATE_PIPE_INSTANCE` (pipe-squatting risk). In tokio (1.53.x) `ServerOptions` exposes `first_pipe_instance(true)` (prevents another process from pre-creating/squatting), `reject_remote_clients(true)` (default), and the `unsafe` `create_with_security_attributes_raw` for a custom DACL (keep this the one audited `unsafe` block in the IPC crate; `first_pipe_instance` is off unless set, so set it explicitly) ([tokio docs](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ServerOptions.html)). Then verify the client with `GetNamedPipeClientProcessId` + `OpenProcess` + `WinVerifyTrust`/publisher check of the client image (recognizing PID-based checks are weaker than macOS audit tokens), and/or `ImpersonateNamedPipeClient` to act with the caller's token so OS ACLs apply.

**Unix domain sockets (Linux/Android desktop helper, macOS fallback).** Place the socket in a 0700 directory owned by the user; check peer credentials with `SO_PEERCRED` (Linux) or `getpeereid()`/`LOCAL_PEERCRED` (macOS/BSD); tokio exposes `UnixStream::peer_cred()` returning uid/gid/(pid). Reject uid mismatch; on macOS prefer XPC because it gives audit-token-based code-signing checks.

**Tauri v2.** Deny-by-default ACL: *permissions* toggle commands, *scopes* constrain arguments (e.g., fs paths), *capabilities* bind permissions to window/webview labels; optional Isolation pattern injects a sandboxed iframe that intercepts and can validate IPC messages (encrypted with SubtleCrypto, keys regenerated each launch) ([Tauri config reference](https://v2.tauri.app/reference/config/), [Tauri 2.0 release](https://v2.tauri.app/blog/tauri-20/)). For Lumen: do **not** enable the generic `fs` plugin for the webview at all; expose only domain commands (`get_scan_summary`, `request_quarantine(plan_id)`), and keep the destructive executor out of the webview process entirely.


### 4. Archives and huge trees
- **Do not open archives.** Lumen's job is to classify artifacts by metadata/evidence; decompressing user archives introduces zip bombs (42.zip-style recursive or overlapping-entry bombs), zip-slip path traversal (`../../` entry names, absolute names, symlink entries), and parser memory-safety exposure, with no safety upside. Treat `.zip/.dmg/.pkg/.tar*` as opaque files: size, mtime, xattrs (e.g. `com.apple.quarantine`), owning app. If a future feature needs to peek (e.g., installer leftovers), do it in a separate sandboxed process with hard caps (entries, total uncompressed bytes, ratio, depth) and never extract to disk.
- **Huge directory trees** (node_modules, `~/Library/Developer/Xcode/DerivedData`, Android `.gradle`, Photos libraries, millions of small files): use an iterative (heap-allocated stack) walker, never recursion; cap depth, entries per directory buffered, and total entries per scan with resumable checkpoints; bound file descriptors (`walkdir` 2.5.0 exposes `max_open`, `max_depth`, `same_file_system`, `follow_links(false)` default, `contents_first` for delete order; it detects symlink loops but does **not** use fd-relative traversal, so it is fine for *scanning* but not for *acting*) ([walkdir docs](https://docs.rs/walkdir/latest/walkdir/struct.WalkDir.html)). For acting, Lumen needs its own fd/handle-relative executor (section 2).
- Resource governance: CPU/IO priority (`setpriority`/`IOPOL_THROTTLE` on macOS via `setiopolicy_np`, Windows `THREAD_MODE_BACKGROUND_BEGIN`), cancellation tokens, per-scan time budgets, and memory caps on the evidence graph (spill to SQLite). A pathological tree should degrade to "partial scan, REVIEW" never to OOM or a hung UI.

### 5. Static analysis and secret scanning
**CodeQL.** Rust support went public preview June 2025 and **GA with CodeQL 2.23.3 (Oct 2025)**; supported in both default setup and advanced setup, build-mode `none`, with Copilot Autofix ([GA changelog](https://github.blog/changelog/2025-10-14-codeql-scanning-rust-and-c-c-without-builds-is-now-generally-available/), [2.23.3](https://github.blog/changelog/2025-10-23-codeql-2-23-3-adds-a-new-rust-query-rust-support-and-easier-c-c-scanning/)). GA languages: C/C++, C#, Go, Java/Kotlin, JS/TS, Python, Ruby, Swift, Rust and **GitHub Actions** workflows ([supported languages](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/)). CodeQL 2.24.0 (Jan 2026) added Swift 6.2/.NET 10 ([changelog](https://github.blog/changelog/2026-01-29-codeql-2-24-0-adds-swift-6-2-support-net-10-compatibility-and-file-handling-for-minified-javascript/)). Default setup = zero-config, GitHub picks languages/query suite; advanced setup = a committed `codeql.yml` giving control over query packs (`security-extended`, `security-and-quality`), path filters, schedules, and custom queries (needed if Lumen writes its own "path built from untrusted name then passed to remove" queries). Code scanning on private repos requires GitHub Code Security ($30/active committer/month; free on public repos) ([GitHub security plans](https://github.com/security/plans)).

**Semgrep / Opengrep.** Semgrep CE engine is LGPL-2.1, but Semgrep-maintained registry rules are under the Semgrep Rules License v1.0 (internal business use allowed; not in competing products/SaaS) ([Semgrep licensing](https://docs.semgrep.dev/licensing)). In Dec 2024 Semgrep moved cross-function taint, fingerprinting and some features to the paid platform; **Opengrep** forked in Jan 2025 (LGPL-2.1, vendor consortium), restoring inter-procedural taint and Windows support, rule/SARIF-compatible ([The New Stack](https://thenewstack.io/opengrep-launches-as-free-fork-after-semgrep-license-shift/); v1.27.1 Aug 2026 per [AppSecSanta](https://appsecsanta.com/opengrep), secondary source). Rust is GA in paid Semgrep Code; in CE Rust is community-supported, single-function only ([Semgrep CE languages](https://docs.semgrep.dev/semgrep-ce-languages)). Verdict: Semgrep/Opengrep is most valuable for **custom project rules** (ban `std::fs::remove_dir_all`, `std::fs::remove_file`, `Path::join` on untrusted input outside the executor crate; ban `dangerouslySetInnerHTML`, `invoke('...')` with raw paths in the UI), not for generic Rust bug-finding where clippy + CodeQL are better.

**Secrets.** GitHub secret scanning and push protection are free for public repos; private repos need **GitHub Secret Protection** ($19/active committer/month) ([GitHub security plans](https://github.com/security/plans)). gitleaks (v8.30.x, [releases](https://github.com/gitleaks/gitleaks/releases/latest)) as a pre-commit/pre-push hook plus CI job covers private repos at zero cost and catches secrets before they leave the laptop.

**Dependency vulnerability scanning.** OSV-Scanner v2.6.0 (Sept 2026) scans `Cargo.lock` and `pnpm-lock.yaml` (incl. git deps), guided remediation for npm/Maven ([release v2.6.0](https://github.com/google/osv-scanner/releases/tag/v2.6.0)). For Rust specifically, `cargo-deny` (advisories + licenses + bans + sources in one `deny.toml`) is the higher-leverage gate, with `cargo-audit` overlapping and `cargo-vet` for human-audited supply chain on high-risk crates (fs, IPC, crypto) ([overview](https://www.systemshardening.com/articles/cicd/rust-cargo-supply-chain-security/), secondary). **Trivy**: useful for container/IaC/SBOM, but note the March 19-23 2026 TeamPCP compromise: a February 2026 `pull_request_target` misconfiguration in the Trivy repo leaked a credential; incomplete rotation let attackers force-push 76 of 77 `aquasecurity/trivy-action` tags and all 7 `setup-trivy` tags (v0.2.0-v0.2.6) to credential stealers and ship malicious `trivy` v0.69.4 (plus malicious v0.69.5/v0.69.6 Docker Hub images via separately compromised Docker Hub credentials) ([GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23), [Microsoft guidance](https://www.microsoft.com/en-us/security/blog/2026/03/24/detecting-investigating-defending-against-trivy-supply-chain-compromise/)). Lumen has no containers in the product, so Trivy is optional; OSV-Scanner + cargo-deny + `pnpm audit` cover it.

### 6. Dependency updates
- **Dependabot**: `cooldown` (`default-days`, `semver-major-days`, `semver-minor-days`, `semver-patch-days`, `include`/`exclude` up to 150 entries, 1-90 days) applies to version updates only; **since 2026-07-14 a 3-day cooldown is applied by default** to version updates in every ecosystem even when unconfigured; security updates bypass it ([options reference](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference), [The Hacker News](https://thehackernews.com/2026/07/github-adds-3-day-dependabot-cooldown.html)). `groups` support `applies-to` (version/security), `patterns`, `exclude-patterns`, `update-types`, `group-by: dependency-name`; `multi-ecosystem-group` combines ecosystems into one PR; `directories` supports globs.
- **Dependabot pnpm gap**: the supported-ecosystems doc still lists **pnpm v7-v10** (npm v7-v11, cargo v1, bun >=1.1.39; cargo private registries unsupported) ([supported ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)), while pnpm is at **v12.9.1** ([pnpm releases](https://github.com/pnpm/pnpm/releases/latest)) and pnpm 11 changed the lockfile to multi-document YAML, which broke Dependabot parsing ([dependabot-core#14919](https://github.com/dependabot/dependabot-core/issues/14919)); the v11 support request #14794 is closed as done but docs were not updated (status unverified).
- **Renovate**: `minimumReleaseAge` (security updates bypass it; since Renovate 42 a missing release timestamp is treated as not-yet-old under the default `minimumReleaseAgeBehaviour=timestamp-required`; for npm Renovate also passes `--before=<date>` during lockfile generation so new transitive versions are held too) ([Renovate docs](https://docs.renovatebot.com/key-concepts/minimum-release-age/)). The docs page states **no built-in global default age**; the often-quoted "3 days for npm" comes from a preset (`security:minimumReleaseAgeNpm`, pulled in by `config:best-practices`) (unverified), so Lumen must set `minimumReleaseAge` explicitly; `helpers:pinGitHubActionDigests` pins and updates action SHAs with version comments; better monorepo grouping, regex managers (e.g., for `rust-toolchain.toml`, Tauri CLI versions in YAML) and tracks pnpm majors faster.
- **pnpm itself** now carries supply-chain controls: `minimumReleaseAge` (added 10.16; **default 1440 min since v11**), `trustPolicy: no-downgrade` (10.21; still opt-in), `blockExoticSubdeps` (added 10.26; **default true since v11**), and `allowBuilds` (replaces the legacy `onlyBuiltDependencies`-style settings in v11) with `strictDepBuilds` (**default true since v11**) for lifecycle scripts ([pnpm dependency-resolution settings](https://pnpm.io/settings/dependency-resolution), [pnpm 11.0 release blog](https://pnpm.io/blog/releases/11.0)). Because these are v11 defaults, Lumen's job is mainly to *not weaken* them (no `minimumReleaseAge: 0`, no blanket `allowBuilds`) and to add `trustPolicy: no-downgrade` explicitly.

### 7. GitHub Actions hardening
**Platform changes since 2025 that shape the design**
- Org/enterprise "allowed actions" policy can **require full-length SHA pinning** and **block** specific actions/versions with `!` (Aug 2025) ([changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/)).
- `pull_request_target` now always runs the workflow file and checkout from the **default branch**; environment branch protections evaluate against the execution ref (enforced 2025-12-08) ([changelog](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)). `actions/checkout` v6 moved persisted credentials out of `.git/config` into `$RUNNER_TEMP` ([community roadmap](https://github.com/orgs/community/discussions/179107)); `actions/checkout` v7 (2026-06-18, backported; enforced 2026-07-20) refuses common pwn-request checkouts of fork PR heads/merge refs in `pull_request_target` **and `workflow_run`** unless `allow-unsafe-pr-checkout` is set; the backport covers all supported majors except v1 ([changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/)).
- **Workflow execution protections GA (2026-09-17)**: actor rules (who) and event rules (which events) at enterprise/org/repo level, targetable per workflow file, evaluate mode, REST API; a default rule **disables `pull_request_target` on public repos** and is auto-enforced **2026-11-02** ([changelog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/)).
- 2026 security roadmap (Mar 2026): workflow `dependencies:` lockfile pinning direct+transitive actions by SHA, scoped secrets, Actions data stream, native L7 egress firewall for hosted runners ([GitHub blog](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)); dependency locking is tracked as "[Public Preview]" on the [roadmap](https://github.com/github/roadmap/issues/1253); the March 2026 blog targeted public preview in 3-6 months and GA in ~6 months, and secondary sources report a technical preview from late June 2026, but as of 2026-10-05 no GA changelog was found (exact syntax and GA status unverified; do not build the pinning policy on it yet).

**Controls**
- `permissions: {}` (or `contents: read`) at workflow top, widen per job. Set org default token to read-only and disable "Allow GitHub Actions to create and approve pull requests" unless release automation needs it.
- Pin every third-party action to a 40-char SHA with a `# vX.Y.Z` comment; let Renovate/Dependabot bump them. The Trivy incident (above) is the concrete reason: tag-pinned consumers silently ran a credential stealer.
- **zizmor** (v1.30.x; audits template injection, excessive permissions, unpinned uses, impostor commits, `pull_request_target`/`workflow_run` dangerous triggers, cache poisoning, `typosquat-uses`, `unsound-ternary`, `adhoc-packages`; SARIF output; `zizmorcore/zizmor-action`) ([releases](https://github.com/zizmorcore/zizmor/releases)) plus **actionlint** v1.7.12 (released 2026-03-30; type/expression/shellcheck lint; knows `macos-26-intel`) ([releases](https://github.com/rhysd/actionlint/releases/latest)), and CodeQL's `actions` language. Because v1.7.12 predates the June 2026 labels (`windows-2025-vs2026`, `windows-11-vs2026-arm`), it may flag newer labels as unknown (unverified); declare any such labels in `.github/actionlint.yaml` rather than disabling the runner-label check.
- **step-security/harden-runner** v2.21.x: audit/block egress on Linux, and since v2.20 block mode on macOS/Windows hosted runners; v2.21.0 added `denied-endpoints` in block mode (an **enterprise-tier** feature, not community) ([releases](https://github.com/step-security/harden-runner/releases), [blog](https://www.stepsecurity.io/blog/harden-runner-block-mode-now-available-for-macos-and-windows-github-hosted-runners)). Caveat: a run of egress-control bypasses was fixed only recently: CVE-2026-25598 (audit-mode logging bypass via `sendto`/`sendmsg`/`sendmmsg`, fixed v2.14.2), CVE-2026-32947 (block-mode bypass by DoH tunnelling through allowed resolvers such as dns.google, fixed v2.16.0), and a separate DNS-over-TCP block-mode bypass (fixed v2.16.0). Domain allowlists are defense-in-depth, not a boundary ([CVE-2026-25598 write-up](https://devansh.bearblog.dev/harden-runner/), [bypass write-up](https://devansh.bearblog.dev/harden-runner-bypass/), [NVD CVE-2026-32947](https://nvd.nist.gov/vuln/detail/CVE-2026-32947)).
- **OIDC** (`id-token: write`) instead of long-lived cloud secrets: Azure Artifact Signing via federated credential; crates.io Trusted Publishing (release-plz >=0.3.146 does the exchange) ([release-plz](https://github.com/release-plz/release-plz)).
- **Artifact attestations**: `actions/attest@v4` (supersedes `actions/attest-build-provenance`, now a wrapper) with `permissions: id-token: write, attestations: write, artifact-metadata: write`; supports `subject-path`, `sbom-path`; verify with `gh attestation verify` ([actions/attest](https://github.com/actions/attest), [attest-build-provenance](https://github.com/actions/attest-build-provenance)). Private/internal repos need **GitHub Enterprise Cloud**. Attestations from hosted runners give SLSA Build L2; L3 requires signing isolated from user build steps, i.e., build in a **reusable workflow** ([GitHub blog on SLSA L3](https://github.blog/enterprise-software/devsecops/enhance-build-security-and-reach-slsa-level-3-with-github-artifact-attestations/)). Immutable releases are GA (Oct 2025): tags/assets locked after publish and releases get signed attestations ([changelog](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)). **Ordering constraint (omitted earlier):** once an immutable release is *published*, uploading an asset fails (HTTP 422), so the release must be created as a **draft**, all signed/notarized assets uploaded, and only then published ([GitHub Docs: immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)). release-please by default creates a *published* release on merge, which conflicts with a later build/sign/upload job; configure release-please to create draft releases (its `draft` option, plus `force-tag-creation` so the tag still exists for the build; option names unverified against the current release-please-action) and have the final release job publish the draft after attestation.
- **Caching**: `Swatinem/rust-cache` (v2) caches `~/.cargo` + `target`, sets `CARGO_INCREMENTAL=0`, prunes stale artifacts; use `save-if: ${{ github.ref == 'refs/heads/main' }}` so PRs read but never write caches (cache poisoning defense; 10 GB repo cap) ([rust-cache](https://github.com/Swatinem/rust-cache)). pnpm: `pnpm/action-setup` + `actions/setup-node` `cache: pnpm`. Never restore caches into release jobs.
- **Runners (Oct 2026)**: `ubuntu-latest`=24.04 (also `ubuntu-26.04`, `ubuntu-slim` 1 vCPU), `ubuntu-24.04-arm`; `windows-latest`=`windows-2025` (VS 2026 since June 2026), `windows-2022`, `windows-11-arm`; `macos-latest`=**macOS 26 arm64** (migration from 15 began 2026-06-15), `macos-15`, `macos-14`, Intel `macos-15-intel`/`macos-26-intel` ([runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [migration changelog](https://github.blog/changelog/2026-05-14-github-actions-upcoming-image-migrations/)). Pin explicit versions (`macos-26`, `windows-2025`, `ubuntu-24.04`) rather than `-latest` so image migrations are deliberate PRs. Private-repo macOS minutes are the dominant CI cost; gate macOS/Windows jobs on path filters and the merge queue.

### 8. Repository governance and release automation
- **Rulesets vs branch protection**: multiple rulesets layer (most restrictive wins), have Active/Disabled (and Evaluate for org/enterprise) enforcement, granular bypass (roles, teams, GitHub Apps), are visible to anyone with read access, and add push rules (file paths/extensions/size), commit metadata rules, tag rules ([About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Availability: public repos on Free; private repos need Pro/Team/Enterprise; org-wide rulesets need Enterprise. Prefer rulesets.
- **Required status checks + merge queue**: checks must also run on the `merge_group` event or the queue stalls; queue has its own check timeout (default 60 min) ([merge queue notes](https://tenki.cloud/blog/github-merge-queue-setup), secondary). `gh pr merge --auto` on a queue-protected branch adds the PR to the queue once checks pass.
- **CODEOWNERS**: require code-owner review on `crates/safety-policy/**`, `crates/fs-executor/**`, `crates/ipc/**`, `.github/workflows/**`, `deny.toml`, `tauri.conf.json`, `capabilities/**`.
- **PR title enforcement**: `amannn/action-semantic-pull-request@v6` recommends `pull_request_target` with `pull-requests: read` ([repo](https://github.com/amannn/action-semantic-pull-request)). Given the Nov 2026 default ban on public repos and pwn-request risk, run it on `pull_request` (types opened/edited/synchronize/reopened; it does no checkout) or an explicit event-rule allowlist for that one workflow file. With squash-merge, the PR title becomes the commit, so title linting replaces most commitlint value; keep commitlint only as a local `commit-msg` hook if desired.
- **Versioning**: `release-please-action@v4` (needs `contents/issues/pull-requests: write`; supports `cargo-workspace` and `node-workspace` plugins and manifest mode for a polyglot monorepo; PRs/tags created with `GITHUB_TOKEN` do not trigger other workflows, so use a GitHub App token for release builds) ([release-please-action](https://github.com/googleapis/release-please-action)). `release-plz` is Rust-crate-centric (changelog via git-cliff, cargo-semver-checks, crates.io publish, Trusted Publishing) ([release-plz](https://github.com/release-plz/release-plz)); Changesets is JS-centric with explicit intent files. Lumen ships apps, not crates: release-please manifest mode fits best.

### 11. Code signing on CI
- **macOS**: Developer ID Application cert + hardened runtime + secure timestamp, then `xcrun notarytool submit <dmg|zip|pkg> --key AuthKey.p8 --key-id ... --issuer ... --wait`, `notarytool log` on failure, `xcrun stapler staple` (staple to `.app`, `.dmg`, `.pkg`; not to bare zips) ([Apple: customizing notarization](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)). Import the p12 into a temporary keychain in the job and delete it after; keep signing in a separate job/environment with required reviewers.
- **Windows**: **Azure Artifact Signing** (formerly Trusted Signing): ~$9.99/month, no HSM token, CI-native; orgs in USA/Canada/EU/UK, **individuals USA/Canada only**; no instant SmartScreen trust (EV no longer bypasses SmartScreen since 2024; reputation accrues to a consistent identity); OV certs now require HSM-stored keys; SignPath Foundation for OSS; MSIX via Store is re-signed free ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Tauri integrates via `bundle.windows.signCommand` calling `artifact-signing-cli` with `AZURE_CLIENT_ID/SECRET/TENANT_ID` ([Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/)); prefer OIDC federated credentials (`azure/login` with `id-token: write`) over a client secret; the GitHub Action is `azure/artifact-signing-action` (formerly `trusted-signing-action`) ([repo issue](https://github.com/Azure/artifact-signing-action/issues/42?timeline_page=1)).

## Implications for Lumen

### A. Security architecture decisions
1. **One destructive-ops crate (`lumen-fs-exec`), handle-relative only.** All moves/deletes go through a single crate that takes a *plan* (list of `{parent_dir_identity, leaf_name_bytes, expected_identity(dev,ino | vol_serial,file_id), expected_size, expected_mtime}`) and executes it by: open scan-root dir handle -> walk components with `openat(O_NOFOLLOW|O_DIRECTORY)` / `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT|BACKUP_SEMANTICS)` -> `fstatat(AT_SYMLINK_NOFOLLOW)` on the leaf and compare identity -> quarantine via `renameat`/`renameatx_np(RENAME_EXCL)`/`renameat2(RENAME_NOREPLACE)`/`SetFileInformationByHandle(FileRenameInfoEx, RootDirectory=quarantine_dir_handle)` -> fsync quarantine dir and the journal. Any mismatch aborts that item to REVIEW. *Rationale:* CVE-2022-21658 proves check-then-act on path strings is unfixable. *Rejected:* `std::fs::remove_dir_all`/`trash` crates on raw paths (no identity re-check, no rollback journal); cap-std alone (good containment, but no identity verification, hard-link races unaddressed, and macOS `O_NOFOLLOW_ANY` not yet used per [issue #179](https://github.com/bytecodealliance/cap-std/issues/179)). Use cap-std (`Dir`) for read-side containment in scanners and `rustix` for the executor's precise flags.
2. **Quarantine = rename within the same volume**, never copy+delete across volumes (copy+delete is non-atomic and doubles TOCTOU windows). If the quarantine dir is on another volume, mark REVIEW or use per-volume quarantine roots (`<volume>/.lumen-quarantine`, owner-only ACL). Permanent deletion happens later, from quarantine only, by handle.
3. **Never cross devices, never follow reparse points/symlinks, never descend into mount points** during both scan and act; count hard-linked files (`nlink>1`) and APFS clones as "not reclaimable" and REVIEW.
4. **Paths are bytes, display is escaped.** Store `OsString`/raw bytes; matching rules operate on normalized+case-folded copies keyed per-volume capability; the UI and Jev receive escaped display strings with bidi/control chars made visible. Treat filenames passed to Jev as untrusted prompt input; Jev outputs evidence scores only (already the design).
5. **IPC**: macOS: XPC + `setCodeSigningRequirement` (quoted Team ID + identifier). Windows: named pipe with explicit DACL (current user SID / logon SID), `first_pipe_instance(true)`, `reject_remote_clients(true)`, plus client image signature check. Linux/Android-desktop: UDS in 0700 dir + `SO_PEERCRED`. The privileged side accepts **plan IDs** produced and stored by the core, not arbitrary paths from the UI. Tauri webview gets no `fs`/`shell` plugin permissions, only domain commands in a narrowly scoped capability file.
6. **No archive opening**; huge-tree scans are iterative, bounded, resumable, and fail closed to REVIEW.
7. **Threat modeling cadence**: maintain `docs/security/threat-model.md` (STRIDE table per DFD element + LINDDUN for telemetry/export/Jev + attack tree for "unintended deletion"); update it in any PR touching CODEOWNERS-protected security paths (PR template checkbox).
8. **Adversarial test suite** (in CI on all three OSes): fixtures that race symlink/junction swaps during execution (a background thread flipping a dir to a link), NFC/NFD twins, case twins, RTL-override names, newline names, invalid UTF-8 (Unix), long paths > 260 (Windows), hard-linked files, read-only files, files open by another process, mount points/bind mounts (Linux), and APFS clone pairs. Property-based tests (proptest) for path normalization; `cargo fuzz` targets for any parser (plist, registry, package manifests).

### C. Minimal workflow skeleton (illustrative)
```yaml
name: ci
on:
  pull_request:
  merge_group:
  push: { branches: [main] }
permissions: {}
concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }
jobs:
  rust:
    strategy:
      matrix: { os: [ubuntu-24.04, windows-2025, macos-26] }
    runs-on: ${{ matrix.os }}
    permissions: { contents: read }
    steps:
      - uses: step-security/harden-runner@<sha> # v2.21.x
        with: { egress-policy: audit }
      - uses: actions/checkout@<sha> # v6/v7
        with: { persist-credentials: false }
      - uses: Swatinem/rust-cache@<sha> # v2
        with: { save-if: "${{ github.ref == 'refs/heads/main' }}" }
      - run: cargo fmt --check && cargo clippy --all-targets --locked -- -D warnings
      - run: cargo test --workspace --locked
  supply-chain:
    runs-on: ubuntu-24.04
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@<sha>
        with: { persist-credentials: false }
      - uses: EmbarkStudios/cargo-deny-action@<sha>
      # osv-scanner, zizmor, actionlint, gitleaks jobs similar
```
Release (separate workflow, `on: push: tags` from release-please, environment `release` with required reviewers): build matrix in a reusable workflow -> sign/notarize -> `actions/attest@v4` with `id-token: write, attestations: write, artifact-metadata: write` -> upload to the **draft** release created by release-please -> publish the draft (it becomes immutable on publish; assets cannot be added afterwards).

## Risks and open questions
- **Repo visibility and plan** decide cost and features: private repos need GitHub Code Security ($30) and Secret Protection ($19) per active committer for CodeQL/push protection, and **Enterprise Cloud for artifact attestations**. If Lumen stays private on Team, attestations are unavailable; fallback is Sigstore `cosign` keyless signing directly (unverified for parity) or making the release repo public.
- **Dependabot pnpm support** for pnpm v11/v12 lockfiles is inconsistent between docs (v7-v10) and the closed issue; re-verify before choosing Dependabot for npm deps.
- **Workflow dependency locking** (`dependencies:` section) status and syntax unverified; may supersede SHA-pinning tooling. Re-check before writing the pinning policy.
- **`RENAME_NOFOLLOW_ANY`** availability and semantics on macOS are unverified; confirm in the Xcode 26 SDK headers. Likewise confirm `O_NOFOLLOW_ANY` behavior with firmlinks (`/System/Volumes/Data`).
- **Windows**: verify `FileRenameInfoEx` + `RootDirectory` behaves as no-replace relative rename on NTFS/ReFS and on Dev Drive (ReFS); behavior on FAT/exFAT removable media and network shares (SMB) differs. POSIX delete semantics require NTFS on Windows 10 1709+ (unverified exact build; the Microsoft Learn struct pages checked list no minimum build). Regardless of build, the executor needs a tested fallback to classic `FileDispositionInfo` when the volume rejects POSIX semantics, as Rust std does.
- **Android/iOS** cannot use most of these primitives (scoped storage, sandbox); the safety model there relies on platform APIs (MediaStore, SAF) covered in docs 05/06. Executor abstraction must accommodate "no handle-relative ops" adapters by restricting them to app-owned/SAF-granted locations.
- **harden-runner** is a mitigation, not a boundary (DNS/DoH bypass history); GitHub's native egress firewall (roadmap) may replace it.
- **Azure Artifact Signing eligibility**: individual developers only in USA/Canada; organization entity required in EU/UK. Decide legal entity early; SmartScreen reputation takes time regardless.
- **macOS 26 runner** only arm64 by default; Intel builds need `macos-26-intel` or cross-compilation; Apple Intel support sunset timing affects the matrix.
- **zizmor/opengrep/OSV versions** above are from release pages and secondary sources on 2026-10-05; pin via SHA and let Renovate track.
- Open: Will Lumen ship a privileged helper on Windows (service) at all, or run fully as the user? This changes the IPC threat model drastically (confused-deputy risk exists only with privilege asymmetry).
